# 门控+C：读回异常复核后继续训练

用户明确要求一次异常后可以继续。此前严格模式将任何两次读回不一致直接判为失败；这些记录不能区分源张量异常与检查副本异常，且没有 CUDA 显存不足报错。新的独立尝试使用 `configs/plan_g1c_recovery_server.yaml`，旧失败目录及证据全部保留。

## 继续条件

仅当同一张量的两份读回字节不同，才执行 `independent_stable_v1` 有界复核：独立直接内存读取、独立克隆，以及设备整数比较；多轮必须一致，并匹配最初两次读取中的一个结果。随后仍须通过原来的数据集重放、Mixup 重放、随机状态及优化器输入前后不变检查。复核不一致、输入重放不一致、非有限损失、CUDA 错误仍会停止。

复核不重新执行训练更新、不跳过 batch、不改学习率、不消耗随机数。每次恢复写入持久事件日志，每步证明记录恢复次数，评测和报告对账并披露。该策略允许在独立复核一致后继续，但不证明异常根因已经修复，也不宣称运行中从未出现异常。

## 固定实验

- G1 门控架构，损失为 `L1 + 0.05 × 平滑图像梯度结构损失`。
- seed 0、1、2，各自从对应原始初始化完成 300000 步；真实 batch 16、FP32。
- 使用已有历史 G1 seed 0/1/2 作为对照，不重复训练基线。
- GPU 0 训练 seed 0；GPU 1 的 seed 1/2 是否并行，由当前完整保护下的实际吞吐测量决定。
- 自动执行初始化/恢复检查、200 步短测、正式训练、四数据集评测、最高 OOD Table 1、多 seed 汇总。

运行目录为 `runs/g1c_recovery`，报告目录为 `reports/g1c_recovery`。当前代码与配置准备就绪；实际启动状态以独立运行的 `pipeline_state.json` 和后续执行记录为准，不能以本文件代替完成证明。

```bash
.venv/bin/python tools/run_g1c_multiseed_pipeline.py --paths configs/plan_g1c_recovery_server.yaml
```
